Sharing is one atomic act, not two. A highlight without its note is an empty
    rectangle, so promoting flips both — in one RPC, or the network drops between two calls and you get
    half-shared rows.

  



create or replace function promote_highlight(p_highlight uuid, p_note uuid default null)
returns highlights
language plpgsql security invoker as $$          -- invoker: RLS still guards it
declare h highlights;
begin
  update highlights set shared_at = now()
   where id = p_highlight
     and profile_id = current_profile_id()          -- enforced here…
     and layer = 'individual'
   returning * into h;
  if not found then raise exception 'not yours to share'; end if;

  update highlight_notes
     set visibility = 'group', updated_at = now(), version = version + 1
   where highlight_id = p_highlight
     and profile_id = current_profile_id()          -- …and again by the policy
     and (p_note is null or id = p_note);
  return h;
end $$;


  
The leader copies nothing. The Group Result reads
  layer = 'group' OR shared_at is not null. “Pulling a note across” is the leader optionally
  re-marking it for emphasis — no copy table, no link column, no two versions of the same thought drifting
  apart.


  

    
The hole this opens in the broadcast trigger. As first written, the trigger fanned
    every highlight row out to ws:{sessionId}, and the topic policy only asks “is this person in
    the workspace” — it never re-checks whether that specific row is visible to them. The table's security
    stayed intact; the broadcast went around it.

    
Fix: pick the topic inside the trigger. Group and promoted rows go to the
    workspace topic; private rows go to user:{profileId}, which only reaches the author's own
    other devices. Same socket, two subscriptions.

    
The rule worth keeping: a broadcast payload is only as private
    as its topic. Never put row data on a topic whose membership is coarser than the row's own policy.

What “Broadcast from Database” means

    a broadcast whose sender is Postgres, not a client
  

  
Realtime has three primitives. Presence tracks who is connected.
  Broadcast puts a message on a topic — normally sent by a client.
  Postgres Changes tails the write-ahead log and pushes row changes. “Broadcast from
  Database” is the second one with the sender swapped: a trigger calls
  realtime.broadcast_changes(), which writes into realtime.messages, and Realtime
  tails that table.

  Dexie, invalidate, re-render.

Outbox

        
    
        
    Nothing queued. The local database and the server agree.
    
      
    
    
    
  
    

  
    
    
    RuleWhat it prevents
    
    
      
    Drain strictly in seq orderA note insert landing before its highlight — a foreign-key violation you would otherwise hit only under bad network.
    
      
    Coalesce updates: debounce 800 ms and replace the pending op for that rowTyping a paragraph queuing two hundred operations instead of one.
    
      
    Inserts are upserts — onConflict: 'id', ignoreDuplicates: trueDuplicates after a crash mid-drain. The id came from the client, so a replay is a no-op.
    
      
    Split failures: 5xx and network → backoff; 4xx → park as failed and surface itA permission error retried forever — a spinner that never stops and no one can explain.
    
        
  
    

  
    Reconnecting, in this order
    
  
    Push, then pull, then resubscribe. Any other order pulls a stale view over changes you
  have not sent yet.
    
  
    For the pull, skip tombstones and diff a manifest instead:
  select id, updated_at from highlights where artifact_id = $1. Ids newer on the server → fetch
  those rows. Ids in Dexie the server did not return, and not _dirty → delete locally. A few KB
  for a few hundred highlights, and it catches deletes — which an updated_at > lastSynced
  query never will.
    

  
    
    
    This needs a column the schema does not have. highlights only carries
    created_at. Add updated_at plus a touch trigger in
    0004_lite.sql, or the manifest diff has nothing to compare.
    
  
    

  
    
    
    Two things not to get wrong. Opening the app offline must not require a token refresh
    — gate local reads on “a stored session exists for this profile”, not on a live check, or you lock people
    out of their own notes exactly when they need them.
    
    
    And on conflict, keep the local text as a second note rather than discarding it.
    Two versions to merge is annoying; a lost paragraph is unforgivable.
