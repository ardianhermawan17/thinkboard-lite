02

Four stores. Pick the right one.

putting a fact in the wrong store is the most expensive mistake available

Why Dexie replaces the entity adapter rather than sitting beside it. Two caches for the same rows is the worst outcome available, so one has to lose. Dexie wins on four counts the product needs: it survives a reload with no network; it holds more than 5 MB; where('[artifactId+page]') is an index hit where selectAll().filter() is O(n) per render; and a row plus its outbox entry land in one transaction, which two dispatches cannot do.

What is preserved exactly is the kernel's role — one normalized mirror, one read surface, every context reads it, it imports nothing. Only the mechanism moved.

Text highlights come from here, never from z2. The Range API gives the exact string for free; a canvas scene would turn it into pixels you then pay to OCR.

z0

PDF.js render output

A plain <canvas>. Windowed to ±1 page around the cursor.

pdfjs-dist
highlight-layer/
├── highlight-layer.tsx          react-konva declarative tree — Layer, Rect, Line
├── use-highlight-layer.ts       logic: live queries, dispatch, derived props
├── highlight-layer.painter.ts   THE EXCEPTION: refs, rAF, batchDraw, live stroke
├── types.ts   ·   highlight-layer.test.ts   ·   index.ts   ← painter NOT exported

The painter contract. It takes a Konva.Layer ref plus plain data and returns a disposer. It imports no store hook, no Dexie, no feature module. pointermove pushes into a ref array; one rAF tick calls batchDraw(). On pointerup the hook converts the buffer to normalized page-relative coordinates and calls the repository — the first and only time that stroke touches state.

That normalization is not a detail. Store viewport pixels and every highlight moves the first time someone zooms, and you will find out weeks later on someone else's tablet.

Peer cursors never enter React. Five peers at 20 Hz is 100 state updates a second, on a tablet that is also rasterising a PDF page and capturing a pointer stream. It will drop frames, and the laggy ink will get blamed on Konva. Refs, imperative paint, one rAF tick.

06

The invariants to add

extend scripts/verify-architecture.mjs before generating any feature code

The reference's I1–I10 are unchanged and still apply. These are the additions. A rule that is not in the script is not a rule — it is a preference the next agent will silently violate.

  • I11No domain row type appears inside a slice's state type.
  • I12persistConfig.whitelist holds no reducerPath and does not hold entities.
  • I13Every Dexie table has at least one query hook in queries/.
  • I14No container destructures data from a command hook.
  • I15Every createApi endpoint traces to a blueprint.commands[] entry.
  • I16Every persisted slice has a ui key, and stripUi is registered in transforms.
  • I17batchDraw | new Konva. | getLayer() appears only in *.painter.ts.
  • I18No *.painter.ts imports @feature/* or @shared/config/*.
  • I19No painter returns a value from clientX/offsetX without passing through shared/utils/geometry.
  • I20No file under components/canvas/ imports motion.
  • I21@supabase/supabase-js only in shared/lib/supabase.ts and features/sync/realtime/channel.ts.
  • I22setAuth() precedes every subscribe().
  • I23useLiveQuery imported only inside features/entities/queries/.
  • I24Every file under components/canvas/ begins with "use client".
  • I25Every blueprint canvas leaf with hasPainter has a painter, and every painter traces to a blueprint entry.

The failure most likely to happen

Generating P7 containers before P4b (the sync kernel). You get containers calling Supabase directly, the outbox never gets used, and offline silently does not work — while everything looks perfect on a good connection. The reference warns about the analogous P7-before-P4 mistake; this is the same one, a layer out. Invariant I21 is what catches it.
